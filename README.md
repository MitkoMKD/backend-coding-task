# Claims API

A .NET 10 API for creating, reading and deleting insurance claims and covers.
The original assignment is in [docs/README.md](docs/README.md).

## Run locally

Requires .NET 10 and SQL Server or SQL Server Express LocalDB. Docker, MongoDB,
and Azure are not needed. Run from the repository root in PowerShell:

```powershell
dotnet restore
dotnet tool restore
$env:ConnectionStrings__MainConnection = 'Server=(localdb)\ProjectModels;Database=ClaimsDb;Trusted_Connection=True;TrustServerCertificate=True'
dotnet ef database update --project Claims.Infrastructure --startup-project Claims
dotnet run --project Claims
```

Use your own SQL Server instance if `(localdb)\ProjectModels` is unavailable.
Open https://localhost:7052/swagger to try the endpoints. If needed, trust the
development certificate with `dotnet dev-certs https --trust`.

**For a fresh setup, use an empty database.** Existing MongoDB data and the
template's audit database are not migrated. An already migrated `ClaimsDb` can
continue to be used. Migrations are applied explicitly, not automatically.

## Endpoints

| Method | Route | Success |
| --- | --- | --- |
| GET | `/Claims`, `/Covers` | 200 with an array |
| GET | `/Claims/{id}`, `/Covers/{id}` | 200, or 404 if missing |
| POST | `/Claims`, `/Covers` | 201 with the resource and a Location header |
| DELETE | `/Claims/{id}`, `/Covers/{id}` | 204, or 404 if missing |
| POST | `/Covers/compute` (query: `startDate`, `endDate`, `coverType`) | 200 with the premium |

IDs and premiums are generated by the server. Invalid input returns 400
ProblemDetails. Deleting a cover with existing claims returns 409.

## Business rules

- Dates use `YYYY-MM-DD`. Cover start is included; cover end is excluded.
- Claims require an existing cover and a claim date within that cover's period.
- Damage cost must be between 0 and 100,000, with at most two decimal places.
- Claim names are required, up to 200 characters. All enum values are validated.
- Covers start today or later (UTC) and last more than zero days, up to one
  calendar year. Leap years are supported; February 29 anniversaries use February 28.

Premium uses a base daily rate of 1250, increased by 10% for yachts, 20% for
passenger ships, 50% for tankers, and 30% for other types.

| Days | Yacht discount | Other types |
| --- | --- | --- |
| 1-30 | None | None |
| 31-180 | 5% | 2% |
| 181 onward | 8% | 3% |

Discounts apply only to days in their band. Additional discounts mean percentage
points, not compounding. The final premium is rounded to two decimals, midpoint
away from zero.

## Design

| Project | Responsibility |
| --- | --- |
| `Claims` | HTTP controllers, exception handling, dependency injection, background worker |
| `Claims.Core` | Models, services, validation, pricing, repository interfaces |
| `Claims.Infrastructure` | EF Core, SQL Server, repositories, migrations, auditing |
| `Claims.Tests` | Unit and integration tests |

Core is independent of the API and Infrastructure. Repositories share one EF Core
unit of work. Types have separate files, with `Interfaces` and `Enums` folders.

## Background auditing

Business changes and pending audit events are saved in one SQL transaction.
A background worker writes the final audits, so HTTP requests do not wait for
that work. Failed writes are retried; pending events survive restarts.

This uses a SQL outbox, not Azure messaging or an in-memory queue. It is designed
for one application instance. A permanently invalid event blocks later events;
dead-letter handling and multi-worker coordination are not implemented.

## Tests

```powershell
dotnet test Claims.Tests/Claims.Tests.csproj
```

Tests cover pricing, validation boundaries, HTTP responses, and audit rollback
and retries. Most tests use mocks or isolated SQLite databases.
To also run the real SQL Server test, set the connection string from setup:

```powershell
$env:CLAIMS_TEST_SQLSERVER = $env:ConnectionStrings__MainConnection
dotnet test Claims.Tests/Claims.Tests.csproj
```

The SQL Server test creates and deletes its own `ClaimsTests_<guid>` database,
so the account needs create-database permission. It is skipped when the variable
is missing. An interrupted run may leave a test database to clean up.

## Limitations

Authentication, authorization, and pagination are outside this exercise.
Do not expose the API publicly without access control. Use a trusted SQL Server
certificate in production and resolve any NuGet security warnings before deployment.
